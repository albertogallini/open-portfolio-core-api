
# PORTFOLIO INPUT DATA MODEL

This is  a **complete, ready-to-use documentation** of the **input data model** (the *transactions* file and its **field-mapping JSON**) and the **output data model** (the *holdings* files generated by the pipeline).  
All field names refer to the constants defined in `oport.fields` – they are reproduced here for clarity.

---

## 1. INPUT DATA MODEL  

### 1.1 Transaction Excel/CSV File (`transaction_file`)

| Column (raw) | Required | Meaning (after mapping) | Example |
|--------------|----------|--------------------------|---------|
| **ISIN** | Yes | `TRANSACTION_FIELD_ISIN` – International Securities Identification Number | `US0378331005` |
| **FIGI** *(optional)* | No | `FIELD_FIGI` – OpenFIGI identifier (used instead of ticker lookup if present) | `BBG000B9XRY4` |
| **Trade Date** | Yes | `TRANSACTION_FIELD_TR_DATE` – date of the buy/sell | `15/03/2024` |
| **Buy/Sell** | Yes | `TRANSACTION_FIELD_BUY_SELL` – direction of the trade | `Buy` / `B` / `Sell` / `S` |
| **Quantity** | Yes | `TRANSACTION_FIELD_QUANTITIY` – number of shares/units (positive) | `150` |
| **Price** | Yes | `TRANSACTION_FIELD_PRICE` – price **per unit** in the instrument’s currency | `123.45` |
| **Currency** | Yes | `TRANSACTION_FIELD_CCY` – ISO-4217 currency of the instrument | `USD` |

> **Note** – The column **names** in the source file are **arbitrary**.  
> The mapping JSON (see below) tells the code which source column corresponds to each required field.

---

### 1.2 Transaction Field-Mapping JSON (`transactions_field_mapping`)

```json
{
  "column_mapping": {
    "<source_column_name>": "<target_field_constant>"
  },
  "columns_name_row": <integer>,
  "data_row_offset": <integer>,
  "date_format": "<python strftime format>",
  "buy_sell_mapping": {
    "<source_value>": "B|V"
  }
}
```

| Key | Type | Description |
|-----|------|-------------|
| **`column_mapping`** | `dict` | Maps **exact** column names from the Excel sheet to the internal constants. **All** of the following keys **must** appear: <br>`TRANSACTION_FIELD_ISIN`, `TRANSACTION_FIELD_TR_DATE`, `TRANSACTION_FIELD_BUY_SELL`, `TRANSACTION_FIELD_QUANTITIY`, `TRANSACTION_FIELD_PRICE`, `TRANSACTION_FIELD_CCY`. <br>Optionally `FIELD_FIGI` if present. |
| **`columns_name_row`** | `int` | Zero-based row index that contains the **column headers**. The code reads `df.iloc[columns_name_row]` as the header row. |
| **`data_row_offset`** | `int` | Zero-based row index **after** which the actual transaction rows start (i.e. skip title rows, totals, etc.). |
| **`date_format`** | `str` | Python `strftime` format used by `pd.to_datetime(..., format=..., dayfirst=True)`. Example: `"%d/%m/%Y"` for `15/03/2024`. |
| **`buy_sell_mapping`** | `dict` | Maps **any** source string to the canonical values **`B`** (buy) or **`V`** (sell). Example: `{"Buy":"B","Sell":"V","Achat":"B","Vente":"V"}`. |

**Example JSON**

```json
{
    "column_mapping": {
        "bs": "buy_sell",
        "QTY": "quantity",
        "Close": "price",
        "CCY": "currency",
        "ticker": "ticker",
        "ISIN": "isin",
        "Trade Date": "transaction_date",
        "unique_id": "figi"
    },
    "buy_sell_mapping":{
        "V": "S",
        "A": "B"
    },
    "date_format": "%d/%m/%Y",
    "columns_name_row": 4,
    "data_row_offset": 5
}
```

## 2. INTERMEDIATE ARTIFACTS (generated automatically)

| File | Purpose |
|------|---------|
| `<output_file_name>_assets.csv` | Unique list of **ISIN + CCY** (plus resolved `FIGI`, `ticker`, `suffix`, `security_type`, `market_sector`). |
| `<output_file_name>_discarded_assets.csv` | Assets for which **no ticker** could be resolved. |
| `<output_file_name>_transactions_tickers.csv` | Cleaned transaction table **with ticker** column; unresolved rows are dropped. |
| `<output_file_name>_yhf_adj_transactions.csv` | Transactions after **split-date alignment** with Yahoo Finance. |

## 3. OUTPUT HOLDINGS DATA MODEL  

The pipeline produces **three** holdings files. All share the same column set; the difference is the **granularity**.

| Column | Type | Description |
|--------|------|-------------|
| **`ticker`** | `str` | Yahoo-Finance ticker (with suffix if needed, e.g. `AAPL`, `GBPUSD=X`). |
| **`isin`** | `str` | Original ISIN (preserved for traceability). |
| **`security_type`** | `str` | `Stock`, `ETF`, `Currency`, … (resolved from FIGI/ticker). |
| **`market_sector`** | `str` | Sector classification (if available). |
| **`date`** | `date` (stored as `YYYY-MM-DD` string in CSV) | Valuation date. |
| **`quantity`** | `float` | **Evaluated quantity** after all buys, sells and corporate actions. |
| **`ccy`** | `str` | Instrument currency (ISO-4217). |

### 3.1 Daily Snapshot – *Holdings* (`_portfolio_holdings.csv`)

* One row **per instrument per transaction date** (only dates where a transaction changes the position).  
* The quantity reflects the **position at the end of that day**.

### 3.2 Unrolled Daily Holdings (`_portfolio_holdings_daily.csv`)

* **One row per instrument per calendar day** from the first transaction date up to the latest price date.  
* Missing days are **forward-filled** from the previous snapshot (quantity stays constant).  
* Zero-quantity positions are **dropped** on the day they reach zero (they re-appear only if a new transaction occurs).

### 3.3 Priced Daily Holdings (`_daily_<ticker>.csv` + concatenated result)

Each ticker gets its own CSV **plus** a master concatenation returned by `impute_positions_logic`.

| Column | Type | Source |
|--------|------|--------|
| **`date`** | `date` | Same as holdings |
| **`ticker`, `isin`, `security_type`, `market_sector`, `quantity`, `ccy`** | – | Copied from holdings |
| **`Close`** | `float` | Yahoo Finance **raw close** (not adjusted for splits). |
| **`FX_RATE`** *(optional)* | `float` | Conversion rate `<instrument_ccy><base_ccy>=X` (e.g. `EURUSD=X`). |
| **`Dividends`** *(optional)* | `float` | Daily dividend amount (if any). |
| **`Stock Splits`** *(optional)* | `float` | Split ratio on that day (0 → no split). |
| **Additional fields** *(if requested via `additional_fields`)* | `any` | Static info from `Ticker.info` (e.g. `marketCap`, `beta`). |

> **Important** – The `Close` price is **de-adjusted** for splits **after** the split date, i.e. historic prices are multiplied by the cumulative split factor so that the price series is comparable to the **raw** Yahoo price on the most recent date.

## OpenFIGI Service Usage in the Pipeline

### Purpose
The **OpenFIGI API** is used to **resolve Yahoo Finance tickers** from **ISIN + Currency** (or directly from **FIGI**) when a ticker is not already known.

This is critical because:
- Yahoo Finance uses **ticker symbols** (e.g., `AAPL`, `VOD.L`).
- The input file contains **ISINs** (e.g., `US0378331005`) and **currencies** (e.g., `USD`).
- There is **no 1:1 mapping** between ISIN and ticker — especially across exchanges.

---

## Step-by-Step Flow of OpenFIGI Resolution

### 1. Input Detection: FIGI vs ISIN+CCY

```python
if fields.FIELD_FIGI not in transactions.columns:
    # → Use ISIN + CCY
else:
    # → Use FIGI directly
```

| Case | Input Fields | Resolution Path |
|------|--------------|-----------------|
| **A** | `ISIN`, `CCY` | → Query OpenFIGI with `idType="ID_ISIN"` |
| **B** | `FIGI` | → Query OpenFIGI with `idType="ID_BB_GLOBAL"` |

---

### 2. Function: `get_tickers_and_suffix()` – The Core Resolver

> This function is **imported from** `oport.ticker_resolver`

```python
from oport.ticker_resolver import get_tickers_and_suffix
```

#### What it does:
- Builds a **payload** for the **OpenFIGI API v3**.
- Sends **batched requests** (up to 100 identifiers per call).
- Returns a DataFrame with:
  - `ticker`
  - `suffix` (e.g., `.L` for London)
  - `exchangeCode`
  - `securityType`
  - `marketSector`

#### Example Payload (ISIN + CCY)
```json
[
  {
    "idType": "ID_ISIN",
    "idValue": "US0378331005",
    "currency": "USD"
  }
]
```

#### Example Payload (FIGI)
```json
[
  {
    "idType": "ID_BB_GLOBAL",
    "idValue": "BBG000B9XRY4"
  }
]
```

---

### 3. API Call Details

| Endpoint | `https://api.openfigi.com/v3/mapping` |
|----------|--------------------------------------|
| Method | `POST` |
| Headers | `Content-Type: application/json` |
| Auth | **API Key** (optional, but recommended for production) |


---

### 4. Response Parsing

#### Sample OpenFIGI Response
```json
[
  {
    "data": [
      {
        "figi": "BBG000B9XRY4",
        "securityType": "Common Stock",
        "marketSector": "Equity",
        "ticker": "AAPL",
        "name": "APPLE INC",
        "exchCode": "US",
        "securityDescription": "Apple Inc."
      }
    ]
  }
]
```

#### Extracted Fields
| Output Column | Source |
|--------------|--------|
| `FIELD_FIGI` | `figi` |
| `ticker` | `ticker` |
| `suffix` | Derived from `exchCode` (via internal mapping) |
| `security_type` | `securityType` |
| `market_sector` | `marketSector` |

---

### 5. Ticker + Suffix Construction

Some exchanges require **suffixes** in Yahoo Finance:
| Exchange | Yahoo Ticker |
|---------|--------------|
| London | `VOD.L` |
| Toronto | `RY.TO` |
| Frankfurt | `SAP.DE` |

The resolver uses a **hardcoded or config-driven map** (not shown in snippet) to append the correct suffix.

---

### 6. Fallback & Error Handling

| Scenario | Behavior |
|--------|---------|
| No match | Row appears in `_discarded_assets.csv` |
| Multiple matches | **First result** is taken (OpenFIGI returns best match first) |
| API error | Logged via `error_collector`, continues with other assets |

---

### 7. Caching (Optional but Recommended)

The code **does not cache** OpenFIGI results by default.

**Recommendation**: Cache results by `(ISIN, CCY)` or `FIGI` → ticker in a local CSV or DB to avoid:
- Rate limits
- Slow startup
- Inconsistent mappings

## Full Data Flow Diagram

```
[transactions.xls]
        ↓
Read → Extract unique (ISIN, CCY) or (FIGI)
        ↓
get_tickers_and_suffix()
        ↓
→ POST https://api.openfigi.com/v3/mapping
        ↓
← JSON response → parse → DataFrame
        ↓
Merge back into transactions → ticker column
        ↓
Drop rows with NaN ticker → _transactions_tickers.csv
        ↓
Proceed to holdings, pricing, etc.
```

## Configuration Tips

| Need | Action |
|------|--------|
| **Use FIGI input** | Include `figi` column in Excel → faster, more accurate |
| **Select exchange** | Set `select_exchange=True` → prompts user to pick from multiple matches |
| **Avoid rate limits** | Add OpenFIGI API key via env var (check `ticker_resolver.py`) |
| **Cache results** | Save `_assets.csv` and reuse with `append=True` |

## Summary: OpenFIGI Role

| Feature | Implemented? | Details |
|-------|--------------|-------|
| ISIN → Ticker | Yes | Via `idType: ID_ISIN` + `currency` |
| FIGI → Ticker | Yes | Via `idType: ID_BB_GLOBAL` |
| Exchange selection | Optional | `select_exchange=True` |
| Suffix handling | Yes | `.L`, `.TO`, etc. |
| Error resilience | Yes | Discards unmapped assets |
| Caching | No | Manual via `append=True` |

---

**Bottom line**:  
**OpenFIGI is the bridge** between **institutional identifiers (ISIN/FIGI)** and **retail data sources (Yahoo Finance)**.  
It runs **once per unique asset**, resolves the **best ticker**, and enables all downstream pricing and holdings logic.
